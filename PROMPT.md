## Non-negotiable rules

- Do not invent metrics, certifications, software skills, job duties, customer approvals, patents, or project details.
- Clearly label every missing detail as `[NEEDS INPUT]`.
- Do not expose proprietary drawings, dimensions, internal specifications, restricted photos, customer-controlled information, or confidential Siemens information.
- Describe projects using only public-safe scope, engineering challenge, my responsibility, general approach, and approved outcome.
- Use first person, active voice, concise technical language, and a professional but approachable tone.
- Build a static site that works on GitHub Pages with plain HTML, CSS, and JavaScript unless I explicitly request a framework.
- Use semantic HTML, responsive CSS, keyboard accessibility, strong color contrast, descriptive link text, and alt text.
- Use relative file paths so the site works as a user site or project site.
- Do not add tracking, cookies, external fonts, or unnecessary dependencies.
- Never overwrite a working file without first showing the specific changes and explaining why they improve the site.

Create a clean, modern engineering aesthetic using deep navy, steel blue, cyan accents, off-white backgrounds, generous spacing, subtle technical geometry, and restrained motion. Avoid generic construction imagery, excessive animations, skill percentage bars, stock-photo clichés, and dense résumé-like pages.

## Work in phases

### Phase 1: Audit
Review my résumé and current website files. Return:
- confirmed facts
- claims that need verification
- confidential-information risks
- missing portfolio content
- the five highest-value improvements

### Phase 2: Information architecture
Propose the page structure, navigation, section order, and project hierarchy. Explain the purpose of each section in one sentence.

### Phase 3: Content
Write polished website copy using only confirmed facts. Provide shorter alternatives for hero text and project summaries.

### Phase 4: Design system
Define colors, typography, spacing, buttons, cards, breakpoints, and accessibility behavior. Keep it framework-free.

### Phase 5: Build
Create or update:
- `index.html`
- `styles.css`
- `script.js`
- `404.html`
- `README.md`
- `assets/` structure

Return complete files, not fragments. Preserve relative paths.

### Phase 6: Quality assurance
Check:
- all internal links and asset paths
- mobile widths of 360 px, 768 px, and 1440 px
- keyboard navigation and focus states
- headings and semantic structure
- color contrast
- résumé download link
- spelling, dates, and metric consistency
- whether every statement is supported by the résumé or my answers

### Phase 7: Publish
Give exact beginner-friendly instructions for:
- naming the repository
- uploading files through GitHub’s web interface
- enabling GitHub Pages from the `main` branch and root folder
- finding the live URL
- updating the site later
- connecting a custom domain as an optional later step

## Start now

Begin with Phase 1. Use my attached résumé and existing site files. Do not generate replacement code until you have completed the audit. If the initial files are already strong, improve them incrementally rather than rebuilding without reason.
